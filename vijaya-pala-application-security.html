I’ve spent the last eight years in application security, and a good while writing software before that, mostly C# and .NET. The development background is hard to shake, and I think it makes me better at this job: a finding is only useful if the person who has to fix it can understand it and act on it.

For the past four years I’ve led application security for a large public-sector eligibility systems estate, the software behind Medicaid, SNAP, and TANF. It is high-volume and document-heavy, parts of it are old, and when something goes wrong it affects real households. That tends to concentrate the mind.

This page is mostly about three pieces of work I designed and built there. They are not grand projects. Each one came out of a specific annoyance, and each one keeps a person, not a tool, responsible for the decision at the end.

Things I’ve built

Help with triaging scanner findings

GitHub Advanced Security does the scanning on this estate: CodeQL for code scanning, Dependabot for vulnerable dependencies, secret scanning for leaked credentials. It works well. It also produces more alerts than a small team can read carefully, and the quality of triage is what suffers first. People start skimming. That is how a real finding gets waved through.

So I built a pipeline to do the reading before a person does. GitHub Actions checks the code out at a pinned commit, so every scan is tied to an exact version and can be re-run against the same code later. A model then goes through the findings, starting with the ones on known-vulnerable components, and writes each one up in a fixed format: where it is, the code that supports it, the reasoning, and how it lines up against what GitHub Advanced Security itself reported. Agree, new, or disputed.

One rule I was not willing to bend: the model never closes a finding, and it never commits code. It writes notes. A person reads them and decides, and GitHub Advanced Security stays the system of record. The day the tool starts deciding is the day reviewers stop reading its output properly.

What it actually buys is time. Reviewers open a finding that already has its evidence assembled and spend their attention judging it instead of hunting for context. That is a modest claim, but it is the whole point.

Reading the documents people send in

Eligibility work runs on paper. People send in pay stubs, letters, forms, and someone has to pull the relevant numbers off them. I built an intake step on Azure Document Intelligence that reads documents like pay stubs and extracts named fields, things like employer, pay period, and gross pay, each with a confidence score attached.

The confidence score is the part that matters. A clean read goes downstream as structured data. A shaky one is visible as shaky, and gets looked at by a person instead of silently becoming a wrong number in a case file. Raw OCR dumped into the next system would have been easier to build and worse in every way that counts.

Browser tests that run themselves

The third piece is the least glamorous. I wrote Selenium tests for the journeys people actually take through these systems, logins, form submissions, the paths caseworkers and applicants use daily, and wired them into GitHub Actions so they run the same way on every build. Failures show up in the pipeline, next to the change that caused them, instead of surfacing weeks later in a manual test cycle.

One boundary, stated plainly because it is easy to get lazy about: the tests run on synthetic data only. They never touch production data. The test data is made up for the purpose, end to end.
