I’ve spent the last eight years in application security, and a good while writing software before that, mostly C#, .NET, and Java. The development background is hard to shake, and I think it makes me better at this job: a finding is only useful if the person who has to fix it can understand it and act on it.

For the past four years I’ve led application security for a large public-sector application systems estate. It is high-volume and document-heavy, parts of it are old, and when something goes wrong it affects real people who rely on these systems every day. That tends to concentrate the mind.

This page is mostly about three pieces of work I designed and built there. They are not grand projects. Each one came out of a specific annoyance, and each one keeps a person, not a tool, responsible for the decision at the end.

01

Things I’ve built

Help with triaging scanner findings

Three scanners, more alerts than a small team can read, and a pipeline that does the reading first.

GitHub Advanced Security does the scanning on this estate: CodeQL for code scanning, Dependabot for vulnerable dependencies, secret scanning for leaked credentials. It works well. It also produces more alerts than a small team can read carefully, and the quality of triage is what suffers first. People start skimming. That is how a real finding gets waved through.

GitHub Advanced Security is not the whole static analysis picture here. I also run Fortify and Veracode static scans across the estate, including the Java applications, and own the triage that follows: sorting true positives from false positives, grouping the findings that share a root cause, and working with the development teams until the real ones are fixed and rescanned. It is slower, less automated work than the pipeline described below, and it is where a lot of the actual risk gets closed.

So I built a pipeline to do the reading before a person does. GitHub Actions checks the code out at a pinned commit, so every scan is tied to an exact version and can be re-run against the same code later. A model then goes through the findings, starting with the ones on known-vulnerable components, and writes each one up in a fixed format: where it is, the code that supports it, the reasoning, and how it lines up against what GitHub Advanced Security itself reported. Agree, new, or disputed.

One rule I was not willing to bend: the model never closes a finding, and it never commits code. It writes notes. A person reads them and decides, and GitHub Advanced Security stays the system of record. The day the tool starts deciding is the day reviewers stop reading its output properly.

What it actually buys is time. Reviewers open a finding that already has its evidence assembled and spend their attention judging it instead of hunting for context. That is a modest claim, but it is the whole point.

Reading the documents people send in

Document intake that extracts the fields, and says how sure it is about each one.

A lot of this work still runs on paper. People send in letters, forms, and supporting documents, and someone has to pull the relevant details off them. I built an intake step on Azure Document Intelligence that reads documents like these and extracts named fields, things like names, dates, and amounts, each with a confidence score attached.

The confidence score is the part that matters. A clean read goes downstream as structured data. A shaky one is visible as shaky, and gets looked at by a person instead of silently becoming a wrong number in an official record. Raw OCR dumped into the next system would have been easier to build and worse in every way that counts.

Browser tests that run themselves

Selenium tests on the real user journeys, wired into every build.

The third piece is the least glamorous. I wrote Selenium tests for the journeys people actually take through these systems, logins, form submissions, the paths staff and end users follow daily, and wired them into GitHub Actions so they run the same way on every build. Failures show up in the pipeline, next to the change that caused them, instead of surfacing weeks later in a manual test cycle.

One boundary, stated plainly because it is easy to get lazy about: the tests run on synthetic data only. They never touch production data. The test data is made up for the purpose, end to end.

Background

The day job behind those projects is the full program: owning static analysis across GitHub Advanced Security, Fortify, and Veracode and the triage that comes with it, dynamic testing with Burp Suite, and following findings through to remediation with the development teams. I also cover the estate’s document imaging side, Datacap and FileNet, which is where scanned documents enter the system and a place where security problems like to hide.
